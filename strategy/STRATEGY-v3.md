## 🧠 なぜThreadsユーザーが動くのか

### 今のThreads東上線投稿（分析済み）
- 「鶴瀬駅徒歩5分の麹カフェ行った」
- 「川越のレコード喫茶いい」
- 「英会話カフェの参加者募集」

**問題**: 散ってる。盛り上がらない。**「理由」がない。**

### コンテストが「理由」を作る

| 要素 | 効果 |
|------|------|
| **「やばい店Top5」** | 明確なゴール。投稿 = ノミネート |
| **投票** | 参加ハードル低い。タップ1回 |
| **発掘感** | 「俺が見つけた」が快感 |
| **駅ごと** | 縄張り意識。「うちの駅が一位」 |
| **発表** | 「結果」が見たい → 再訪問 |

### モチベーション構造

```
投稿する理由: 「この店をTop5にノミネートしたい」
  ↓
投票する理由: 「推しの店を一位にしたい」
  ↓
見る理由: 「結果が知りたい」「新しい店発見したい」
  ↓
戻る理由: 「次はどの駅のコンテスト？」
```

## 🏪 「やばい店」とは

### 定義
> **「知る人ぞ知る、行く価値のある店」**

| 条件 | 例 |
|------|-----|
| 駅徒歩10分以内 | アクセス良い |
| SNSフォロワー < 1,000 | まだ知られてない |
| 何か「やばい」がある | 味、店主、雰囲気、メニュー |
| 実在する | 営業中・アクセス可能 |

### 路線あたりの数
```
1路線 × 30駅 × 1-2件/駅 = 30-60件の「やばい店」
```
**Top5に選ばれた店 = エリート**。価値が生まれる。

## 🏆 コンテスト設計

### フロー

```
1. 投稿期間（2週間）
   → Threads:「#東上やばい店 鶴瀬駅 ○○カフェ 投稿して！」
   → プラットフォーム: URL + 駅名 + 一言 → 投稿完了

2. 投票期間（1週間）
   → 「行ってみたい」= 投票
   → 1日1投票（デバイス制限）

3. 結果発表
   → Top5自動発表ページ（静的生成）
   → Threadsにリンク投稿
   → 「やばい店マップ」完成

4.  aftermath
   → 来店増 → 店舗がSNSで感謝 → 次回も参加
   → メディア「東上線やばい店Top5」→ 無料PR
```

### ルール（最小限）

| ルール | 内容 |
|--------|------|
| 1投稿 | 1駅・1店舗 |
| 投票 | 1日1回（デバイス制限） |
| 期間 | 投稿2週間 → 投票1週間 |
| 順位 | 投票数で自動決定 |
| 発表 | Top5 + 全ノミネート一覧 |

## 👤 一人運用の仕組み

### やること（運営側）

| タスク | 頻度 | 時間 | 自動化 |
|--------|------|------|--------|
| Threads投稿 | 週2回 | 10分 | 半自動（定型文） |
| 荒らし対応 | 発生時 | 5分 | 手動承認（初期） |
| 結果発表 | 月1回 | 30分 | 自動生成 |
| 店舗連絡 | 月1回 | 20分 | テンプレメール |

### 自動化できること

| タスク | 方法 |
|--------|------|
| 投票集計 | Firebaseクエリ一発 |
| Top5発表 | 静的ページ自動生成 |
| Threads通知 | API連携（後から） |
| 来店効果計測 | 保存数・クリック数 |

### 自動化できないこと（最初）

| タスク | 理由 |
|--------|------|
| 荒らしフィルタ | AI判定は精度不足 → 手動承認で安全 |
| 店舗とのやり取り | 温度感・信頼関係は人間が必要 |
| メディア対応 | 取材対応は運営の「顔」が必要 |

## ⚠️ リスクと対策

| リスク | 対策 |
|--------|------|
| 投稿が来ない | Threadsで直接募集・知人に依頼 |
| 荒らし投稿 | 初回手動承認・URLドメイン制限 |
| 投票の水増し | デバイス制限 + IP制限 |
| 店舗が炎上 | コメント機能なし・投票のみ |
| 飽きられる | コンテスト期間限定・次回の告知 |
| 他路線展開失敗 | 東上線で成功実証してから |
